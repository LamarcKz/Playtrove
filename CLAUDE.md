# CLAUDE.md — Playtrove

Guia de trabalho compartilhado do Codex e do Claude Code neste projeto: o que o app faz, caminhos, comandos, convenções, testes, privacidade, Git, versões e documentação.

Este arquivo é a fonte única das regras de trabalho dos dois agentes e mantém o nome `CLAUDE.md` para continuar compatível com o Claude Code. O `AGENTS.md` é o ponto de entrada do Codex: orienta a leitura integral deste guia e a consulta ao `ESTRUTURA.md`, sem duplicar as regras.

As orientações dirigidas ao "Claude", inclusive o fluxo e as autorizações de Git, testes e lançamentos abaixo, também se aplicam ao Codex. Pedidos atuais do usuário e instruções do ambiente têm precedência; estas regras não alteram permissões nem liberam execução em modo de planejamento.

**O estado do projeto, o histórico e as notas do mantenedor ficam fora do repositório.** Este guia só tem o que é técnico (ver "Privacidade" e "Documentação").

## O projeto

- **Aplicativo:** **Playtrove**, biblioteca de jogos para desktop (Windows) no estilo Playnite/Steam: reúne os jogos dos emuladores, as conquistas e o tempo jogado.
- **Referência visual:** Playnite, modo Desktop (modo Detalhes).
- **Ícone:** um baú de tesouro com a fechadura de play, em traço branco no quadrado azul (sem controle nem direcional, para não lembrar outros apps). Fica em `build/icon.ico` (o .exe, o instalador e a janela no `npm run dev`; até 32 px o traço é mais grosso, para continuar legível), `docs/logo.svg` (README) e `AppLogo.tsx` (barra do topo e Sobre).
- **Stack:** Tauri 2.12 + Rust 1.99 (edição 2024) + rusqlite 0.40 (SQLite embutido) na parte de trás; Vite 7 + React 19 + TypeScript 7 + Tailwind CSS 4 + shadcn/ui (base Radix, estilo `radix-nova`) + lucide-react na interface. Até a 0.7.x, o app era Electron 44 + electron-vite 5 + better-sqlite3 13; na troca, a interface React continuou a mesma, falando com o Rust pela ponte `lib/tauriApi.ts` (o mesmo `window.api` de antes), e os testes da lógica do processo principal passaram a ser os do Rust.
- **Para compilar:** Node.js, Git e o Rust estável (MSVC), que no Windows pede o Visual Studio Build Tools com C++ (ver "Como compilar" no README).
- **Repositório:** público, `LamarcKz/Playtrove`. A `main` é sempre igual à última release (a versão atual está no `package.json` e em `gh release list`); o trabalho acontece na `desenvolvimento` (ver "Git e GitHub"). O site e os guias ficam no `LamarcKz/Playtrove-site` (ver "Site e guias").
- **A biblioteca começa vazia:** os jogos entram pelas pastas de ROMs; os 12 jogos de exemplo existem só nos testes.
- **Ideias para depois:** ficam no "Roadmap" do `README.md` (lembrar modo e filtros ao reabrir, tema claro, links dos jogos...), nunca como código que ainda não faz nada. Onde mexer para cada uma está em `ESTRUTURA.md`, na seção "Onde implementar cada funcionalidade futura".

## O aplicativo

Regras de produto que o código segue. O mapa dos arquivos de cada parte está no `ESTRUTURA.md`.

### Janela e abas

- O app abre com a janela maximizada, ou em tela cheia quando a preferência de inicialização estiver ligada. Restaurada, a janela fica com o que couber na área livre da tela (no robô dos testes, a tela tem 1024×768).
- A barra do topo e o menu lateral têm a mesma cor, sem linha entre eles, e formam uma moldura; o conteúdo fica encaixado nela, com o canto arredondado.
- A barra do topo tem logo, busca, o botão de filtros, o seletor de modos (Detalhes, Grade, Lista e Kanban), o controle conectado e os botões da janela. O botão do meio mostra "restaurar" quando a janela está maximizada (canal `window:state`).
- O menu lateral é só de ícones: Biblioteca, Estatísticas, Conquistas, Emuladores e Configurações.
- **Leitura das quatro abas:** Estatísticas, Conquistas, Configurações e Emuladores usam `ContentPage.tsx`, com conteúdo centralizado de até 1600 px, margens de 16/24 px e títulos de seção de 16 px. Configurações mantém todas as seções montadas: Geral, Status e Sobre numa pilha; Metadados e Conquistas na outra. As pilhas e as seções de Emuladores ficam lado a lado a partir de 1120 px de conteúdo útil; abaixo disso, empilham. Listas, caminhos, formulários e ações podem quebrar linha, e as barras estatísticas passam para baixo do nome/valor nos cartões estreitos. `tests/app/layout.spec.ts` confere dimensões, rolagem, textos longos e preservação dos formulários.
- A versão do app fica em Configurações → "Sobre".

### Biblioteca e filtros

- A Biblioteca abre no modo **Detalhes, que é o principal**; também existem os modos Grade (com o status numa faixa embaixo de cada capa), Lista e **Kanban**.
- O Kanban tem uma coluna por status, e arrastar um jogo muda o status dele (salvo no banco). **Todas as colunas cabem na tela, sem rolagem lateral**, com fundos neutros, nas cores do app. No Kanban, o painel de detalhes abre por cima do quadro. Trocar de modo fecha esse painel e mostra só a biblioteca; o jogo escolhido continua destacado.
- A Lista tem as colunas Nome, Status, Plataforma, Biblioteca, Tempo jogado, Nota, Dificuldade e Conquistas.
- **Filtros num painel na direita**, como no Playnite (o botão ao lado da busca abre e fecha). Favoritos e Recentes (últimos 30 dias) em caixinhas no topo; embaixo, **um seletor por filtro**, para o painel não crescer demais quando entrarem filtros novos: um campo que abre a lista com caixinhas, com várias opções marcáveis e a quantidade de jogos em cada uma. Todos funcionam: Status, Tempo jogado, Nota, Dificuldade, Biblioteca, Plataforma e, com os metadados, Gênero, Desenvolvedora, Publicadora e Ano de lançamento; um filtro sem dados em nenhum jogo aparece desativado ("Sem dados ainda"). A busca ignora maiúsculas e acentos.
- **Favorito e Recentes não são status:** o status é um só por jogo; o favorito é uma marca à parte, que combina com qualquer status; e "Recentes" é calculado pela última vez jogado, então muda sozinho com o tempo. Por isso os dois são filtros, não abas.
- Menu **Mais** de cada jogo: avaliar, escrever a análise, baixar metadados, marcar como favorito (a estrela aparece ao lado do nome), escolher ou remover o vídeo de fundo e a música tema, reativar suas buscas automáticas e mostrar a ROM no Explorador.

### Tela cheia

- **Janela ↔ tela cheia, como no Playnite:** o botão "Tela cheia" da barra do topo (com texto) ou o F11 entram na tela cheia nativa do Tauri/Windows; nela, o menu principal (Options ou o botão "Menu" da barra) tem "Voltar ao modo janela", "Minimizar", "Sair do Playtrove", "Configurações" e "Jogo aleatório", e o F11 também volta. A apresentação só muda após confirmar o estado nativo (`window:state`, com `isMaximized` e `isFullscreen`); sair restaura a posição, o tamanho e o estado maximizado anteriores. O desktop mantém a página, a busca, os filtros, o modo e a seleção enquanto fica oculto, e recupera o foco ao voltar.
- **Aniki ReMake portado:** a tela cheia reproduz o tema Aniki ReMake 3.6.0 (MIT, aviso em `THIRD-PARTY-NOTICES.md`), desenhada num palco de 1920×1080 ajustado ao monitor (`AnikiStage.tsx`), com a paleta padrão dele (dourado sobre azul-escuro, tokens `--aniki-*`) e a fonte Exo 2. Os addons de outros autores que o Aniki usa são recriados, sem copiar código; imagens, sons e avatares com arte de terceiros não são copiados.
- **Welcome Hub, perfil e painéis rápidos:** como no assistente do Aniki, a tela cheia abre no Welcome Hub ou na biblioteca (`startDestination`, padrão Hub), só ao abrir o app; alternar janela/tela cheia preserva onde a pessoa estava. O Hub tem páginas (L1/R1): o perfil (avatar, nome, "Fã de" o gênero mais jogado, tempo total, plataforma favorita e os números da biblioteca e do mês) e a atividade (último jogado, mais jogado, adicionado por último e um nunca jogado). O perfil (`profileName` e `profileAvatar`, nas preferências da tela cheia) usa avatares próprios do Playtrove. O Acesso rápido (painel à esquerda) tem configurações, jogo aleatório, atualizar biblioteca e energia (o menu principal); as Opções rápidas (à direita), a música, o volume e onde abrir.
- **Biblioteca horizontal e Detalhes Signature:** a biblioteca segue a interface Padrão do Aniki: barra do topo (perfil, Hub, Menu, Buscar, troféus pegos de cada tipo, controle e relógio), o nome da coleção no canto, nome do jogo sobre a arte, etiquetas (favorito, troféus, plataforma), a legenda dos botões e a faixa de capas com o destaque dourado; confirmar uma capa abre os detalhes no layout Signature do Aniki: nome sobre a arte, painel de vidro com a capa (nota e dificuldade sobre ela), estúdio e ano, os botões Jogar, Troféus, Descrição e Opções, tempo jogado, última vez, status, gêneros e a barra de conquistas, e o trailer em miniatura à direita. A descrição e a análise ficam no painel de descrição (botão de informações); os troféus, no painel de troféus do Aniki: cabeçalho com capa, progresso e os pegos de cada tipo, cartões com insígnia, raridade, data e tipo, ordenar (padrão, nome, data, raridade, tipo), mostrar (todas, desbloqueadas, faltam) e revelar ocultos. A barra do topo mostra os troféus pegos de cada tipo em toda a biblioteca. As coleções são Todos, Recentes (últimos 30 dias, ordenados pela última vez jogado) e Favoritos, com seleção própria durante a sessão. A busca por título ignora maiúsculas e acentos e consulta a biblioteca inteira, independentemente da coleção; limpar a busca restaura a seleção e a tela anteriores.
- **Entrada (mapa do Aniki):** DualSense por USB ou Bluetooth, direcional/analógico esquerdo para mover o foco, × para confirmar (na capa, abre os detalhes), ○ para voltar (na biblioteca, não sai da tela cheia), □ para jogar, △ para as opções do jogo, L3 para buscar, L1/R1 para coleções (no Hub, para as páginas), Options para o Acesso rápido (segurar: preferências) e Create para o Hub (segurar: Opções rápidas). Options, Create e △ agem ao soltar; segurados por 500 ms, disparam a segunda ação (`FULLSCREEN_HOLD_MS`). O leitor entrega também L2, R2, R3, PS e touchpad. Teclado: setas, Enter, Escape e F11 para voltar ao modo janela; mouse continua disponível. A navegação fica limitada ao painel visível. Reconexão e reativação exigem soltar os botões antes de aceitar ações, e só as direções se repetem. A validação física de navegação USB/Bluetooth ainda está pendente; pacotes e eventos sintéticos não a substituem. DualSense Edge continua apenas com o indicador de conexão/bateria.
- **Dados comuns:** favorito, status, nota, dificuldade e análise usam os mesmos comandos e banco do desktop. O teclado virtual de busca/análise aceita maiúsculas, acentos, pontuação, espaços, exclusão, cursor e quebra de linha na análise; cancelar preserva o texto anterior. Os detalhes das conquistas reutilizam os dados e as linhas do desktop, com filtros e revelação de troféus ocultos.
- **Mídia e preferências:** a faixa salva acompanha a seleção, com reprodução e volume independentes do desktop. Preferências ficam em Configurações → Geral e no painel da tela cheia; início em tela cheia vem desligado, música ligada e volume em 20%. O vídeo salvo toca sem som no trailer em miniatura dos detalhes (`AnikiTrailerCard.tsx`), com espera de 600 ms e respeito a movimento reduzido; o fundo fica com a imagem. Áudio, vídeo e navegação pausam sem foco, com a janela oculta ou durante um jogo; não há dois players ambientes ativos ao trocar de apresentação.
- **Jogar e voltar:** a tela cheia bloqueia um segundo lançamento durante a abertura ou com um jogo em execução e mostra o estado de execução; quando o processo termina, mantém o jogo selecionado nos detalhes. O emulador conserva suas próprias configurações de janela. Configuração de emuladores e pastas continua no desktop; a biblioteca vazia oferece esse caminho. Hub, configuração completa por controle, perfil, outros layouts, temas, ferramentas e conectores ficam no roadmap.

### Status

- **Os status não têm cor:** aparecem só com o nome, em todo o app, e a tela de Status também não tem cor.
- Os 9 padrão, na ordem do Kanban: Planejo jogar, Parei por um tempo, Abandonei, Jogando, Fazendo 100%, Platinando, Zerado, 100% e Platinado.
- **Configurações → Status:** renomear, mudar a ordem, criar e apagar status (os jogos do status apagado vão para outro, escolhido na hora) e as duas regras automáticas: jogo novo → "Planejo jogar"; primeiro jogo → "Jogando".

### Avaliação

- O menu **Mais** tem **"Avaliar jogo…"** (janela com a **nota em estrelas** e a **dificuldade em pimentas**, as duas de meia a cinco, guardadas de 1 a 10) e **"Escrever análise…"** (janela só com o texto; vira "Editar análise…" quando já existe). A análise é separada da nota.
- O ícone do "Avaliar" é o `CircleStar` (o `StarHalf` do lucide parece quebrado). A pimenta é um ícone próprio (`icons/PepperIcon.tsx`), porque o lucide não tem.
- Nos Detalhes, a nota e a dificuldade ficam **ao lado do Jogar e do Mais, no estilo da Steam** (rótulo pequeno em cima), e "Minha análise" fica **em cima da Descrição**, com uma linha separando. O painel lateral mostra as duas coisas também; a Lista tem as colunas Nota e Dificuldade, e os filtros, Nota e Dificuldade (faixas de ícone inteiro, com a meia na faixa de baixo).

### Emuladores e o botão Jogar

- **Aba Emuladores:** PCSX2, DuckStation, RetroArch, RPCS3, PPSSPP (PSP), Dolphin (GameCube e Wii) e Azahar (3DS). O app acha os emuladores sozinho (atalhos do menu Iniciar e da Área de Trabalho, depois os lugares de instalação comuns e, por fim, as pastas vizinhas às dos já achados — é assim que um emulador portátil, numa pasta ao lado dos outros, aparece), e o usuário pode trocar o executável. No RPCS3, a varredura pega as ISOs e as pastas de jogo extraídas (PS3_GAME/USRDIR/EBOOT.BIN), com o nome vindo do PARAM.SFO.
- Cada pasta de ROMs tem emulador, core (no RetroArch) e console, sugeridos pelo nome da pasta (PS2 → PCSX2, GBA → RetroArch com mGBA, PSP → PPSSPP, GameCube e Wii → Dolphin, 3DS → Azahar). "Procurar" põe na biblioteca as ROMs novas, com o nome limpo (sem "(USA)" e afins); o que já está não entra de novo, e tirar uma pasta não tira os jogos. O resultado aparece em avisos rápidos no canto de baixo. Com a biblioteca vazia, um botão leva até essa aba.
- **Botão Jogar:** abre a ROM no emulador, **com a configuração do próprio emulador** (o app não força tela cheia: cada um tem a sua configuração de janela), e mostra "Em execução" enquanto ele está aberto. Quando o emulador fecha, soma o tempo jogado e guarda a última vez jogado (sessões com menos de 3 s não contam, e menos de um minuto aparece como "1 min"); fechar o app com o jogo aberto registra o tempo até ali. **A exceção é o RetroArch, que abre maximizado em janela:** o app espera a janela dele aparecer e maximiza (se ele estiver em tela cheia na configuração dele, fica como está). Detalhes em "Emuladores", nas convenções.

### Tempo jogado e Estatísticas

- **Tempo jogado dos emuladores:** o app lê o que os emuladores registram por conta própria e mostra o maior entre esse tempo e o que ele mesmo contou, com a última vez mais recente das duas. Assim o que foi jogado abrindo o emulador direto também aparece. Esse tempo também entra na atividade das Estatísticas: na primeira leitura de um jogo, tudo o que o emulador já tinha registrado vira uma sessão no dia da última vez jogado, e só se esse dia for dos últimos 30 dias; depois disso, entra o que aparecer de novo a cada leitura. O que o app já contou é descontado, para não aparecer duas vezes.
- **Aba Estatísticas:** resumo (jogos, tempo jogado, média entre os jogados, jogados nos últimos 30 dias), os 10 mais jogados, jogos por status (sem cor), por plataforma e por biblioteca, a atividade dos últimos 30 dias (gráfico de colunas com dica ao passar o mouse ou com o foco do teclado, e a versão em tabela), os jogados por último e os nunca jogados. As barras usam uma cor só (`--chart-bar`, com o contraste conferido). A atividade por dia vem das sessões de jogo (tabela `play_sessions`): o que o app contou e o que os emuladores registraram.

### Metadados e imagens

- A capa dos jogos de emulador vem do **libretro-thumbnails** (a caixa escaneada que o RetroArch usa, achada pelo nome exato da ROM; sem chave); o IGDB dá descrição (em inglês), gêneros (no idioma do app), desenvolvedora, publicadora e lançamento; o SteamGridDB dá o fundo e a capa dos jogos que o libretro não tiver. **O ícone da lista é um pedaço da capa** (os ícones do SteamGridDB, feitos por fãs, variam demais). No IGDB, quando dois resultados têm o nome igualmente parecido, fica o jogo em si (e não um hack, mod ou DLC dele, pelo `game_type`) e, depois, o lançado primeiro.
- As chaves são criadas por quem usa o app e salvas em Configurações → Metadados, que tem o passo a passo e confere a chave antes de salvar. Elas ficam criptografadas pelo Windows (DPAPI, `secrets.rs`) e nunca voltam para a tela. Download em fila, um jogo de cada vez, com "Metadados 3/7" na barra do topo e um aviso no fim; jogos novos de uma pasta de ROMs ganham os metadados sozinhos (dá para desligar). O que não for encontrado agora não apaga o que o jogo já tinha.
- **Onde as imagens aparecem:** ícone na lista do modo Detalhes, **capa acima do nome** e arte de fundo nos Detalhes (o conteúdo começa bem embaixo, para a arte aparecer inteira), capa na Grade (com a faixa do status **logo embaixo da área da capa, sem cobrir a imagem**, e os cantos de baixo retos) e fundo atrás da capa no painel lateral (Grade, Lista e Kanban).
- **Proporção das capas:** as imagens aparecem inteiras, sem cortes, distorção ou preenchimento desfocado. Na Grade, cada capa fica centralizada numa área fixa **2:3**, de até 384 px de altura, com fundo neutro nas sobras; essa área mantém as mesmas dimensões durante carregamento, sem imagem ou em erro, quando aparece o desenho padrão. Os cartões ficam alinhados pelo topo e a faixa do status começa logo abaixo da área comum; títulos e status longos podem quebrar linha, então a altura total dos cartões ainda pode variar. No modo Detalhes e no painel lateral, o quadro acompanha a proporção original, cabendo em até 160 × 288 px e 176 × 320 px, respectivamente. `tests/app/covers.spec.ts` verifica as dimensões, a arte inteira e o alinhamento em diferentes larguras, sem capturas de tela.
- **Trailer automático por jogo:** com o IGDB configurado, a fila de metadados busca os vídeos associados ao jogo e baixa um trailer do YouTube para os dados do app, em MP4 H.264, até 720p e 100 MiB. A primeira utilização prepara as ferramentas automaticamente, sem instalação global. Jogos novos seguem a opção de baixar metadados sozinhos; o botão **Baixar metadados** também inclui jogos antigos com metadados, mas sem uma busca de trailer concluída. Não achar trailer registra a busca; uma falha de download gera aviso e permite tentar de novo, sem perder descrição ou imagens.
- **Vídeo de fundo por jogo:** no menu Mais, **Escolher vídeo de fundo…** abre a seleção de um MP4 ou WebM local e guarda uma cópia nos dados do app, com prioridade sobre o trailer automático; **Remover vídeo de fundo** tira essa cópia e desativa novas buscas automáticas para aquele jogo, mantendo o arquivo original. Sem vídeo, **Desativar vídeo automático** permite manter só a imagem; **Usar trailer automático** reativa a busca e coloca o jogo na fila. O vídeo se repete sem som somente no modo Detalhes, com reprodução automática; com movimento reduzido, a reprodução começa pausada. A imagem de fundo permanece durante o carregamento e se a reprodução falhar. Trocar de jogo ou modo encerra a reprodução anterior, e ocultar a janela pausa o vídeo. O painel lateral continua usando a imagem.

### Música tema

- A faixa salva do jogo selecionado toca offline, em repetição, nos quatro modos da Biblioteca desktop: Detalhes, Grade, Lista e Kanban. Um único player preserva a reprodução ao trocar de modo; trocar de jogo faz a saída e a entrada suaves. Sem faixa, não há áudio. A reprodução pausa com a janela oculta ou sem foco, com qualquer jogo em execução, ao sair da Biblioteca e ao entrar em tela cheia; reprodução e volume do desktop ficam em Configurações → Geral. A tela cheia usa preferências próprias (ver acima). Um clique ou tecla na Biblioteca recupera um bloqueio de reprodução automática do WebView2.
- **Configurações → Geral:** reprodução e volume de 0 a 100; os padrões são reprodução ligada e volume em 20%. Em **Metadados**, a preferência de buscar músicas automaticamente para jogos novos é independente da reprodução e da busca automática dos outros metadados. Um pedido explícito de metadados também busca músicas ausentes, mesmo com o automático desligado, sem refazer imagens/descrição quando só o áudio falta. Consultas sem resultado podem ser repetidas explicitamente. Candidatas incertas ficam guardadas, e **Revisar músicas** aparece depois que a leva inteira terminar; a pessoa pode ouvir, escolher ou ajustar a consulta pelo jogo/faixa. A ação **Agora não** conserva a revisão após reiniciar. As ferramentas dos trailers são reutilizadas, sem nova conta.
- **Menu Mais:** **Escolher música tema…** importa MP3, M4A ou WAV de até 32 MiB com prioridade manual; cancelar ou falhar conserva a faixa anterior. **Buscar outra música…** permite rever/substituir inclusive uma faixa automática já existente. **Remover música tema** apaga só a cópia e desativa o automático do jogo; **Usar música automática** reativa e conserva a faixa anterior até uma nova instalação válida. O original local permanece intacto, e respostas de buscas/prévias antigas não sobrescrevem escolhas posteriores.

### Conquistas (RetroAchievements)

- Quem usa o app salva o nome e a **Web API Key** do RetroAchievements em Configurações → Conquistas (conferidos no site antes de salvar; a chave fica trancada pelo Windows). Quem desbloqueia são os emuladores, logados na conta; o app só lê o site: logo depois de salvar, a cada 5 minutos com o app aberto, 20 s depois de fechar um jogo e no botão "Atualizar", e mostra um aviso no canto quando aparece uma conquista nova.
- **Padrão do PS3 para todas:** as conquistas aparecem como os troféus do RPCS3, com quantos de cada tipo, pegos e total (**platina 0/1 · ouro 1/3 · prata 2/4 · bronze 1/3**), no cartão, na janela e na lista de jogos da aba. O RetroAchievements não tem tipo: ele sai dos **pontos**, que lá dizem a dificuldade (**bronze até 9, prata de 10 a 24, ouro com 25 ou mais**, `gradeForPoints()`), e a **platina** é uma só, que vale quando todas as conquistas do jogo foram pegas.
- **Visualmente, só os troféus:** a raridade (pela porcentagem de jogadores do site: **Comum** 50% ou mais, **Rara** 15 a 50%, **Muito rara** 5 a 15% e **Ultrarrara** menos de 5%) fica só como texto, sem cor, na linha de cada conquista ("Bronze · Comum · 96% dos jogadores · 5 pontos").
- **Onde aparece:** um **cartão pequeno à direita do título nos Detalhes** (em janela estreita, desce para baixo dos botões), com o progresso, os troféus de cada tipo, as últimas insígnias e "Ver todas" (janela com todas, filtráveis); o troféu com "3/6" na lista da esquerda, na capa da Grade e na coluna Conquistas da Lista; e a **aba Conquistas** (resumo, gráficos por dia e por mês, os jogos com o progresso e as 12 desbloqueadas por último). Não é filtro.
- Os jogos são achados no catálogo do site pelo console e pelo nome (os números da série têm que bater; hacks e "subsets" ficam de fora); o PS3 não tem conquistas lá.

### Troféus do PS3 (RPCS3)

- O app lê os troféus que o próprio RPCS3 guarda, sem conta e sem internet, e mostra nos mesmos lugares das conquistas: o cartão dos Detalhes vira "Troféus", com quantos de cada tipo (**Bronze, Prata, Ouro e Platina**, as cores do PS3 — o padrão que as conquistas do RetroAchievements seguem também; não há raridade, porque o RPCS3 não sabe quantos jogadores pegaram), e a aba Conquistas junta tudo.
- Antes da primeira vez que o jogo abre no RPCS3 (é quando ele instala os troféus), o cartão mostra só o aviso de quando eles vão aparecer, em vez de ler a lista do disco.
- Os **troféus ocultos** que faltam aparecem como "Troféu oculto", com o botão "Mostrar ocultos" na janela com todos. A platina do PS3 é o troféu de platina (os pacotes extras não contam), e um troféu novo vira aviso ("Troféu desbloqueado: X"). O app relê a pasta do RPCS3 a cada minuto, logo depois de fechar um jogo, depois de uma varredura e no botão "Atualizar".

Por isso o `latest.yml` vai em toda release.

Sem a privada, o app instalado não aceita mais nenhuma atualização. Nunca pôr a chave privada, nem uma cópia dela, no repositório.

### Dados de quem usa o app

- **Segurança dos dados:** as chaves das APIs ficam trancadas pelo Windows (DPAPI, `secrets.rs`) e nunca voltam para a tela; a biblioteca, as notas e as análises ficam no arquivo do banco, na pasta do usuário, sem criptografia (criptografar o banco inteiro arriscaria perder tudo se a senha do Windows fosse redefinida). Um `.env` guardaria as chaves às claras e é para configuração de quem desenvolve, não para os dados de quem usa o app. É uma decisão tomada: não propor mudança sem o mantenedor pedir.
- **Chaves das APIs:** quem cria e salva as chaves (IGDB, SteamGridDB e RetroAchievements) é quem usa o app, no próprio app: um agente nunca digita chaves. Os testes usam serviços de mentira.
- **Nunca diagnosticar o banco por cópia com o app rodando:** copiar um SQLite em uso dá uma cópia rasgada, que parece danificada (sem tabelas) mesmo com os dados inteiros. Se precisar olhar, abrir só para leitura, e de preferência com o app fechado. Por isso o app grava sem WAL e confere/conserta o banco ao abrir (ver "Banco de dados", nas convenções).

## Convenções de código

- **TypeScript** `strict`, com `noUnusedLocals` e `noUnusedParameters`.
- **Estilo** do shadcn: aspas duplas, sem ponto e vírgula, 2 espaços e vírgula no fim de listas. Exports nomeados (`export function X`).
- **Nomes de arquivo:** componentes e páginas em PascalCase (`GameCard.tsx`); outros módulos em camelCase (`mockGames.ts`); `components/ui/` segue o shadcn (minúsculas). No Rust, snake_case (`rom_scanner.rs`).
- **Imports:** na interface, `@/` = `src/renderer` e `@shared/` = `src/shared`.
- **Textos e idiomas:** nenhum texto da tela fica escrito direto no código. Tudo sai de `src/shared/i18n/`: `ptBR.ts` é o dicionário base e `en.ts` precisa ter as mesmas chaves (o TypeScript confere). Texto novo = nos dois dicionários. Na interface, `const { t } = useI18n()` (as funções de `lib/` recebem o `t` ou o `t.locale`); no Rust, `text()` de `src-tauri/src/i18n.rs` (os erros que vão para a tela, as janelas do Windows e o aviso do conserto do banco), que lê o `src-tauri/messages.json`, gerado dos dicionários pelo `npm run tauri:mensagens` (as funções viram modelos com `{0}`, `{1}`...; o `backendMessages.test.ts` acusa quando ele ficou para trás). Plural e concordância ficam em funções do dicionário (ex.: `t.common.games(3)`); datas e números usam o `t.locale` (Intl). Nos passos a passo, `**negrito**` vira `<strong>` (`RichText`). Comentários, commits, testes e erros internos (que nunca aparecem) continuam em português. O idioma escolhido fica na tabela `settings` (`language`); sem escolha, vale o do Windows (português → português; qualquer outro → inglês). A janela recebe o idioma no endereço (`?lang=en`), para a primeira tela já sair certa. `tests/unit/i18n.test.ts` acusa texto solto na interface e sobra de português no inglês.
- **Cores:** só em `src/renderer/styles/globals.css` (variáveis CSS + `@theme inline`). Os componentes usam classes como `bg-background` e `bg-play`, nunca cor fixa. O fundo escuro também está em `BACKGROUND_COLOR` (`src-tauri/src/window.rs`); mudar os dois juntos.
- **Tema:** o escuro é o padrão, pela `class="dark"` no `<html>` (`src/renderer/index.html`).
- **Interface ↔ Rust:** o formato do `window.api` fica em `src/shared/ipc.ts` (`AppApi`), e a ponte `src/renderer/lib/tauriApi.ts` liga cada função ao comando do Rust de mesmo nome, em snake_case (`games.setStatus` → `games_set_status`, em `src-tauri/src/commands.rs`, com os valores em camelCase). Os comandos recebem os valores crus (`serde_json::Value`), conferem tudo pelo `validation.rs` e devolvem o erro como a mensagem que a tela mostra (`AppError`, já no idioma do app). Um comando que espera a internet ou o disco leva `#[tauri::command(async)]`, para não travar a janela. Os tipos que vão para a tela seguem os de `src/shared` (`serde` com `rename_all = "camelCase"`). Os avisos do Rust para a tela (`app.emit`) têm os nomes de `EVENTS` (`src/shared/ipc.ts`), e cada `on...` da ponte devolve uma função para parar de ouvir. Não passar eventos do React para funções de `window.api` (usar `() => fn()`). A receita de um comando novo está no `ESTRUTURA.md`.
- **Rust:** a parte de trás fica em `src-tauri/src/`, um módulo por assunto (o mapa está no `ESTRUTURA.md`). Formatação pelo `cargo fmt` (`rustfmt.toml`), o `cargo clippy` limpo, e testes no fim de cada arquivo (`#[cfg(test)]`), rodados pelo `npm run test:rust` (`cargo test`: banco em memória e pastas temporárias, nunca os dados do computador). Comentários e testes em português, como no resto. O `cargo` fica em `%USERPROFILE%\.cargo\bin` (um terminal aberto antes da instalação do Rust não o enxerga).
- **Conferir na tela:** sempre pelo `npm run dev` (a janela com a marca DEV), nunca por uma janela que pareça o app instalado — por isso o app de release (o instalador e a portátil) não é aberto para conferir. Para olhar e clicar na janela do dev sem atrapalhar: `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223` antes do `npm run dev` e o Playwright com `chromium.connectOverCDP`, sem chamar `browser.close()`, que fecharia a janela. Avisar o usuário antes de abrir janelas, inclusive as dos testes. Conferências manuais com emuladores instalados usam sempre uma pasta de dados temporária e nunca abrem jogos.
- **Rodando o app para testar:** pode haver um `npm run dev` aberto; não encerrar esse processo. O `npm run dev` recompila e reabre o app a cada arquivo salvo do Rust: numa mudança que mexa nos dados do usuário, salvar numa ordem em que nenhum passo intermediário estrague nada (e o arquivo pode estar momentaneamente preso pelo dev; se uma gravação falhar com "UNKNOWN", tentar de novo). O `npm run dev` usa a cópia da biblioteca (`%APPDATA%\Playtrove Dev`) e o app instalado, a de verdade: os dois podem ficar abertos juntos (o WebView2 de cada pasta de dados fica em `<pasta>\webview`), e nada do que se testa no dev chega aos jogos de verdade. Os testes do app usam o app dos testes, compilado à parte (`src-tauri/target/testes`), e podem rodar com o dev aberto.
- **Claude Code (configuração do projeto):** o `.claude/settings.json` vai para o GitHub e vale para quem usar o Claude Code neste repositório, então não pode ter caminho com o nome de usuário nem chave. Libera sem perguntar só o que não abre janela nem envia nada: `npm run typecheck`, `build`, `test:unit`, `versao`, `test:rust`, `tauri:mensagens` e `web:build` e o `cargo build`, `fmt` e `test`; o Git de leitura (`status`, `diff`, `log`, `show`, `branch`, `fetch` e `grep`); e o `gh` de leitura (rodadas, checks, Pull Requests e releases). Bloqueia o que este guia proíbe: `push --force`, `--no-verify` (e o `commit -n`), `reset --hard`, `git clean` e ler ou alterar a biblioteca de verdade (`%APPDATA%\Playtrove`) pelas ferramentas de arquivo. O `npm test`, o `test:app`, o `npm run dev` e o `dist` continuam pedindo licença, porque abrem janelas ou assinam versões (o pedido serve de aviso ao usuário); commits, pushes e Pull Requests também passam pela confirmação do Claude Code, mesmo com o fluxo de "Git e GitHub" autorizado. As regras valem para a ferramenta Bash (Git Bash); no PowerShell, o Claude Code continua perguntando. O app cria as sessões em worktree dentro do projeto (`.claude/worktrees/`): elas e o `.claude/settings.local.json` (as licenças dadas só num computador) ficam fora do Git, e uma sessão em worktree começa sem `node_modules` (rodar `npm install` nela antes de compilar ou testar).
- **Controles (`hidapi`):** `src-tauri/src/controllers.rs` separa descoberta (a cada segundo), bateria econômica (leituras curtas a cada 5 s, com fechamento do handle) e input opt-in de tela cheia. O leitor de input mantém um único handle por aparelho enquanto habilitado, usa esperas de 20 ms, aproveita os relatórios para atualizar a bateria e publica só mudanças (`controllers:input`). A bateria cede o acesso ao input; a negociação Bluetooth fica fora do bloqueio de leitura. `controllers_set_input_enabled` só habilita com janela nativamente em tela cheia, focada e sem jogo em execução; saída, perda de foco, destruição da janela e lançamento desabilitam a leitura. O parser puro `controller_input.rs` aceita USB 0x01/64 bytes e Bluetooth simples 0x01/10 ou 78 bytes e completo 0x31/78 bytes (incluindo id). O transporte vem do aparelho, nunca só do id 0x01; o analógico esquerdo tem zona morta e o direito não navega. Sequência, geração e neutralidade descartam ações antigas e botões mantidos após reativação/reconexão. DualSense navega; Edge só informa bateria. No Bluetooth, os feature reports 0x05/0x09 solicitam o modo completo para ler a bateria. No status, os 4 bits de baixo dão o nível (0–10), e os de cima, a carga (0 = descarregando, 1 = carregando, 2 = completa); 0x29 significa completa com nível 9 (95%), sem forçar 100%. Testes automáticos não inicializam HID real: usam pacotes e eventos sintéticos; a conferência física é separada.
- **Janela:** sem a barra do Windows (a barra do topo é a da interface; arrastar pelo `data-tauri-drag-region`, que vale só no próprio elemento). A janela nunca sai do endereço da própria interface (`on_navigation`), e a CSP (`index.html`) só aceita scripts do app, imagens do protocolo das imagens, vídeos de `http://playtrove-video.localhost`, áudios de `http://playtrove-music.localhost` e a ponte com o Rust. No app de verdade, uma janela só (abrir de novo traz para a frente a que já está aberta); no dev e nos testes, não, para eles abrirem junto com o app instalado.
- **Código limpo:** o repositório só tem o que funciona. Nada de função vazia, campo da tela sem dado, comentário `// TODO:` ou `export` que ninguém importa; o que falta fazer vai para o "Roadmap" do `README.md`.
- **Dependências:** a interface não tem nada em `dependencies`: React, shadcn, Tailwind, a `@tauri-apps/api`... vão em `devDependencies`, porque o Vite empacota tudo dentro do app. Se o `npx shadcn add` instalar algo em `dependencies`, mover para `devDependencies`. As do Rust ficam no `src-tauri/Cargo.toml`. O `allowScripts` do `package.json` nega de propósito o script de instalação do esbuild; não aprovar.
- **Versões presas por compatibilidade:** Vite fica na 7 e `@vitejs/plugin-react` na 5.x (a 6.x exige Vite 8). O motivo antigo (o electron-vite 5, que não suportava o Vite 8) saiu com o Electron, então dá para atualizar os dois juntos numa tarefa própria, conferindo as peer dependencies.
- **shadcn/ui:** os arquivos de `components/ui/` são código do projeto. Preferir customizar via `className`. O `cn()` vem do pacote `cn` (oficial do shadcn). O `TooltipProvider` e o `ToastProvider` (avisos rápidos, `useToast()`) ficam no `App.tsx`.
- **Select do Radix em formulário:** ele coloca um `<select>` escondido depois do botão. Num campo com rótulo em cima, usar `flex flex-col gap-*`, e não `space-y-*` (a margem iria para o botão e desalinharia os campos; aconteceu em `RomFolderList.tsx`).
- **Tooltip em volta de toggle:** o `TooltipTrigger asChild` sobrescreve o `data-state` do `ToggleGroupItem` (confirmado no app). Destacar o item ativo por `aria-checked`, como em `LibraryTools.tsx`.
- **Estado compartilhado:** o que é controlado na barra do topo e usado na página (busca, modo de exibição) fica no `App.tsx` e desce por props. A biblioteca (`useLibrary`) também fica lá.
- **Banco de dados:** SQLite (`rusqlite`, com o SQLite embutido), só no Rust. Tabelas: `statuses`, `games`, `emulators`, `rom_folders`, `settings` (migração 1), `play_sessions` (migração 2, uma linha por vez que um jogo foi jogado) as colunas do tempo dos emuladores (migração 3; a 4 manda ler esses registros de novo, para o tempo antigo entrar na atividade por dia), as da avaliação do usuário (migração 5: `rating`, `difficulty`, `review` e `evaluated_at`), as das conquistas (migração 6: as tabelas `ra_catalog`, `ra_games` e `achievements`, e as colunas `ra_game_id` e `ra_matched_at` em `games`), as dos troféus do PS3 (migração 7: as tabelas `trophy_sets` e `trophies`, e as colunas `trophy_set` e `trophy_checked_at` em `games`), a dos idiomas (migração 8: a coluna `preset` em `statuses`, que diz qual status padrão cada um é, e os gêneros passam a ficar como o IGDB escreve, em inglês), a do vídeo de fundo (migração 9: `background_video` em `games`, somente o nome da cópia interna) e a dos trailers automáticos (migração 10: `background_video_mode`, com `auto`, `manual` e `disabled`, e `background_video_checked_at`; vídeos existentes ficam em `manual`) e a das músicas tema (migração 11: `theme_music`, `theme_music_mode`, `theme_music_checked_at` e `theme_music_revision`). As 8 primeiras são as mesmas que o app tinha em Electron (até a 0.7.x), na mesma ordem: o banco de quem vem de lá abre direto. **Sem WAL** (`journal_mode = DELETE`): cada gravação vai direto para o arquivo do banco. Assim nada fica só num arquivo de registro à parte, que pode se perder se o app for fechado à força (e o arquivo do banco sozinho já conta a história inteira). Ao abrir, o app confere (`quick_check`) e, se estiver danificado, conserta: copia para um banco novo tudo o que ainda dá para ler, acerta o que ficou sem par, guarda o arquivo danificado ao lado (nada é apagado) e avisa o usuário (`database.rs`). As tabelas vêm de `migrations.rs` (`PRAGMA user_version`): mudar a estrutura = migração nova no fim da lista, nunca editar uma que já saiu. As consultas ficam em `library.rs` e nos módulos de cada assunto, em funções que recebem a conexão (assim dá para testar com um banco em memória). Depois de gravar, `notify_library_changed()`; o `useLibrary` recarrega sozinho.
- **Status:** vêm do banco (`Status`: id, nome e posição), sem cor. Nos componentes, usar `useStatuses()` e `useStatusName()` (o `StatusesProvider` fica no `App.tsx`). Os 9 padrão têm a marca `preset`, e o nome deles sai do dicionário (`statusPresets`), no idioma do app: a biblioteca já chega com o nome traduzido. Renomear tira a marca, e um nome novo não pode repetir o de outro status em nenhum dos idiomas.
- **Emuladores:** o que o app sabe de cada um fica em `PRESETS` (`src-tauri/src/emulators.rs`): nome do executável, lugares comuns, extensões e argumentos. **Nada de forçar tela cheia:** vale a configuração de cada emulador. **A exceção é o RetroArch, que abre maximizado em janela** (só ele, por enquanto): `maximize: true` no preset faz o `launcher.rs` chamar o `emulator_window.rs` com o número do processo, que procura a janela principal do processo a cada 200 ms, por até 10 s, e chama o `ShowWindow` com `SW_MAXIMIZE` direto pelas funções do Windows; só numa janela com o botão de maximizar, então o emulador em tela cheia na configuração dele fica como está. Para outro emulador abrir maximizado, basta o `maximize: true`. Os argumentos precisam fazer o emulador **fechar junto com o jogo** (`-batch` no PCSX2 e no DuckStation, `--no-gui` no RPCS3, `--pause-menu-exit` no PPSSPP, `-b -e` no Dolphin), porque o tempo jogado é contado até o processo terminar. O Azahar não tem opção para isso (conferido no código dele): com ele, o tempo conta até o Azahar ser fechado. O emulador abre separado do app: fechar o app não fecha o jogo (e registra o tempo até ali). As sessões abertas ficam na memória (`launcher.rs`). A detecção lê os atalhos do menu Iniciar e da Área de Trabalho pelo próprio Windows (COM, em `system_sources.rs`).
- **Metadados:** tudo em `src-tauri/src/metadata/` (IGDB, SteamGridDB, libretro-thumbnails, a escolha do resultado certo, o download de um jogo e a fila). Cada imagem tem uma ordem de fontes e vale a primeira que baixar (capa: libretro → SteamGridDB → IGDB; fundo: SteamGridDB → IGDB). Os pedidos saem pelo `ureq` (`metadata/http.rs`), e cada módulo recebe quem faz os pedidos por parâmetro (os testes passam uma internet de mentira). Chave errada ou falta de internet param a leva inteira (`MetadataError::Stop`); outros erros pulam só aquele jogo. As chaves passam por `metadata/credentials.rs` (que guarda pelo `secrets.rs`); a interface só recebe o `MetadataConfig`, sem as chaves. Os gêneros ficam como o IGDB escreve, e a tela mostra no idioma do app (`genreLabel()`, com os nomes em `genres` nos dicionários).
- **Chaves das APIs (`secrets.rs`):** criptografadas no mesmo formato do `safeStorage` do Electron, para as chaves salvas na 0.7.x continuarem valendo: uma chave AES protegida pelo Windows (DPAPI) no arquivo "Local State" da pasta de dados e cada segredo em AES-GCM ("v10"), guardado na tabela `settings`.
- **Conquistas:** tudo em `src-tauri/src/achievements/` (o cliente da API, a escolha do jogo certo, as insígnias, o banco, a rodada de atualização e o serviço que agenda). A API do RetroAchievements leva a Web API Key no parâmetro `y` (chave errada = 401 → para a rodada). O site pede para guardar as listas grandes: os consoles valem 30 dias e o catálogo de cada console, 7 dias (tabela `ra_catalog`). A rodada normal só busca os jogos com conquista nova (`API_GetUserRecentAchievements`), os nunca atualizados e 2 dos atualizados há mais de um dia (a raridade muda devagar); salvar a conta e o "Atualizar" buscam todos. Na primeira vez de um jogo, nada vira aviso (seriam as conquistas antigas). A biblioteca só mostra o progresso dos jogos atualizados com a conta atual (`ra_games`); tirar ou trocar a conta apaga o que era dela. As insígnias ficam em `<dados do app>/images/achievements/` (`123.png` e a apagada, `123_lock.png`), pelo mesmo protocolo das capas.
- **Troféus do RPCS3:** também em `src-tauri/src/achievements/` (`trophy_files.rs`, `trophy_store.rs`, `trophy_sync.rs` e `trophy_icons.rs`); `views.rs` junta os dois tipos para as telas. O RPCS3 guarda cada conjunto em `<pasta dele>/dev_hdd0/home/<usuário>/trophy/<código>/` (o usuário ativo vem do `persistent_settings.dat`, `[Users] active_user`, e o `dev_hdd0` pode ter sido mudado no `config/vfs.yml`): o `TROPCONF.SFM` (XML, já no idioma do RPCS3, com `ttype` P/G/S/B, `hidden` e o pacote extra em `gid`), o `TROPUSR.DAT` (binário big-endian: marca 0x818F54AD; na tabela 6, um registro de 0x70 bytes por troféu, com o id, se foi pego e a data em microssegundos desde 0001-01-01, UTC) e as imagens `TROPnnn.PNG`. O jogo é ligado ao conjunto pela pasta `PS3_GAME/TROPDIR/<código>` do disco (ISO ou pasta; em `discs.rs`) ou, se não der, pelo nome. Só é relido o conjunto cujos arquivos mudaram (tamanho e data). Na primeira leitura de um conjunto, nada vira aviso. As imagens são copiadas diminuídas (96 px, pela biblioteca `image`) para `<dados do app>/images/trophies/<código>/<id>.png`. Data sem sentido no arquivo (antes de 2006 ou no futuro) fica como a hora em que o app percebeu.
- **Imagens dos jogos:** ficam em `<dados do app>/images/<id do jogo>/cover|icon|background.<ext>`. A interface mostra pelo protocolo `playtrove-img` do Rust (`images.rs`; no Windows, `http://playtrove-img.localhost/<id>/cover.png`), que só entrega arquivos dessa pasta e lê o disco fora da linha da janela; o `?v=` no endereço (a data do download) faz a tela trocar a imagem na hora. A CSP (`index.html`) libera `img-src http://playtrove-img.localhost`. Sem imagem (ou se ela não carregar), os componentes mostram o desenho padrão.
- **Vídeos de fundo:** `videos.rs` importa MP4/WebM escolhidos pelo diálogo nativo, conferindo extensão e assinatura do contêiner, para `<dados do app>/images/<id do jogo>/background-video-<identificador>.<ext>`, e associa os trailers baixados à mesma pasta. O banco guarda só o nome interno, o modo (`auto`, `manual` ou `disabled`) e a última busca concluída; `library.rs` devolve `backgroundVideoUrl`, `backgroundVideoMode` e `backgroundVideoCheckedAt`. Cancelar ou falhar conserva o vídeo anterior, e remover ou substituir apaga somente a cópia interna. Um resultado automático só é associado se o jogo continuar no modo automático ao terminar o download. O protocolo dedicado `playtrove-video` lê fora da linha da janela, aceita `GET`/`HEAD` e intervalos de bytes com respostas de até 2 MiB, sem carregar o vídeo inteiro; só serve nomes internos e caminhos canônicos dentro da pasta do jogo. A CSP libera o protocolo em `media-src`. `GameDetailsBackdrop.tsx` restaura a fonte da mídia em cada setup antes de reproduzir (incluindo o ciclo extra do StrictMode no DEV), cuida da pausa automática, do movimento reduzido e da imagem de reserva; `tests/app/backgroundVideo.spec.ts` usa um WebM sintético e dados temporários para conferir o fluxo sem mídia pessoal.
- **Download de trailers:** `metadata/igdb.rs` traz os ids dos vídeos associados ao jogo; `metadata/download.rs` busca o trailer junto dos outros metadados. `metadata/trailer_downloader.rs` usa yt-dlp **2026.10.21** e Deno **2.9.8**, preparados por `metadata/trailer_tools.rs` em `<dados do app>/tools`, de releases oficiais com SHA-256 fixo conferido antes de executar. Não usar instalação global, configuração externa, cookies, plugins, atualização automática ou componentes remotos das ferramentas. O download prefere vídeo sem áudio e aceita somente MP4 H.264 de até 720p e 100 MiB, sem conversão ou FFmpeg. O `metadata/trailer_tools_process.rs` executa sem shell nem janela, com ambiente restrito e JobObject associado antes da execução; ao terminar, falhar ou esgotar o prazo, encerra também os descendentes, conferidos por testes com subprocessos do próprio harness. O limite de 100 MiB conta os bytes realmente recebidos, e o prazo total de 180 s inclui a preparação das ferramentas. Os testes usam um downloader falso no Rust e `/trailers/<id>.mp4` no servidor local de `tests/app/fakeMetadataServer.ts`; `automaticTrailers.spec.ts` nunca acessa YouTube nem prepara ou executa essas ferramentas.
- **Músicas tema:** `music.rs` valida extensão, assinatura e limite de 32 MiB dos arquivos locais e guarda cópias em `<dados do app>/images/<id do jogo>/theme-music-<identificador>.<ext>`. A migração 11 acrescenta `theme_music`, `theme_music_mode` (`auto`, `manual`, `disabled`), `theme_music_checked_at` e `theme_music_revision`; essa revisão invalida downloads iniciados antes de uma escolha, remoção ou reativação. `library.rs` entrega `themeMusicUrl`, `themeMusicMode` e `themeMusicCheckedAt`. O protocolo `playtrove-music` aceita `GET`/`HEAD` e intervalos de até 2 MiB fora da linha da janela, restrito a nomes internos e caminhos canônicos dentro da pasta do jogo; a CSP o libera em `media-src`. `MusicConfig` persiste reprodução, volume e busca automática na tabela `settings`, e `music:config` sincroniza `useMusicConfig` entre Configurações e Biblioteca.
- **Busca e reprodução de música:** `metadata/theme_downloader.rs` separa busca e download por ID: até três consultas com dez resultados, no máximo trinta IDs, normalização de nomes/aliases e campos opcionais. Identidade do jogo/edição e representatividade da faixa são julgamentos distintos; nomes próprios da OST são aceitos e popularidade é apoio, sem garantir a faixa mais famosa. Áudio AAC nativo em M4A, até dez minutos e 32 MiB, sem FFmpeg/Python/conversão, com prazo de 180 s por operação e cancelamento do processo/descendentes. `music_search.rs` persiste gerações, candidatas e origem em `music_searches`/`music_sources` (migração 12); revisão do jogo e geração protegem a instalação. `music_previews.rs` oferece cache separado com um download ativo, até dois arquivos/64 MiB e protocolo `playtrove-music-preview` autorizado por token/revisão; confirmar reaproveita o arquivo. Fechar cancela/limpa o temporário. `MusicReviewDialog.tsx` e `musicPreviewPlayer.ts` coordenam escuta e faixa ambiente, preservando as preferências de reprodução e volume. `LibraryThemeMusic.tsx` mantém seleção nos quatro modos, atraso de 300 ms e rampas de 500 ms. Testes usam somente servidor local e áudio sintético.
- **Tempo jogado dos emuladores:** `src-tauri/src/emulator_playtime.rs` lê os registros de cada um (PCSX2 e DuckStation: `playtime.dat` por código do disco; RPCS3: `persistent_settings.dat`; PPSSPP: a seção `[PlayTime]` do `ppsspp.ini`, no `memstick` ao lado dele ou em Documentos\PPSSPP; Dolphin: `Config/TimePlayed.ini`, em milissegundos, na pasta `User` (portátil), em Documentos\Dolphin Emulator ou no AppData\Roaming; Azahar: `sysdata/play_time.bin`, 16 bytes por jogo, na pasta `user` (portátil) ou no AppData\Roaming\Azahar; o Dolphin e o Azahar não guardam a última vez jogado; RetroArch: um `.lrtl` por jogo) e `src-tauri/src/discs.rs` tira o código do disco da ISO ou do BIN/CUE (e o nome dos jogos de PS3 do PARAM.SFO), do PARAM.SFO dos jogos de PSP (ISO e EBOOT.PBP), do começo dos discos de GameCube e Wii (ISO, RVZ, WIA, WBFS e CISO) e o id do programa dos jogos de 3DS (.3ds/.cci e .cxi), lendo só alguns bytes. O código fica guardado na coluna `serial`. O que a tela mostra é o maior entre o tempo do app e o do emulador, para nunca contar duas vezes.
- **Testes:** `tests/unit` (Vitest: a lógica da interface), os do Rust (no fim de cada arquivo de `src-tauri/src`, pelo `npm run test:rust`: banco em memória e pastas temporárias) e `tests/app` (Playwright com o app dos testes: o build de desenvolvimento do Tauri com a interface embutida, compilado em `src-tauri/target/testes` pelo `scripts/build-test-app.mjs`; o `launchApp()` abre ele e liga o Playwright na janela pela depuração do WebView2, numa porta livre). O Playwright é só dos testes: ele abre o app numa pasta de dados temporária e clica como uma pessoa; não vai junto com o app. O app lê (em `test_mode.rs`, e só no build de desenvolvimento, nunca no de release) `PLAYTROVE_DATA_DIR` (pasta de dados), `PLAYTROVE_SAMPLE_GAMES=1` (os 12 jogos de exemplo), `PLAYTROVE_SKIP_EMULATOR_DETECTION=1` (não procura os emuladores do PC), `PLAYTROVE_SYSTEM_LANGUAGE` (finge o idioma do Windows: o `launchApp()` usa português, e os testes de idioma, inglês), `PLAYTROVE_METADATA_TEST_SERVER` (o IGDB, o SteamGridDB, o libretro-thumbnails e o RetroAchievements de mentira de `tests/app/fakeMetadataServer.ts`), `PLAYTROVE_FAKE_UPDATE` (uma versão nova de mentira, ex.: `9.9.0`, para o aviso de atualização) `PLAYTROVE_HIDE_DEV_MARK=1` (sem a marca DEV, só para as capturas do README) e `PLAYTROVE_REMOTE_DEBUGGING_PORT` (a porta em que a janela aceita o Playwright: o próprio app passa ao WebView2, porque o Windows do robô ignora a variável `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`; se a janela não abrir, o erro diz como ela estava e o fim do registro do WebView2); os troféus do RPCS3 vêm de uma pasta de mentira, com os arquivos de `tests/fakeTrophies.ts`; os testes do app sempre usam uma pasta temporária — inclusive para as pastas do Windows de onde vêm os tempos dos emuladores (Documentos e AppData\Local viram subpastas dela). Os testes que leem o banco precisam esperar o app terminar de gravar. Com a pasta de dados dos testes, o `test_hooks.rs` troca a janela de "Abrir" por uma resposta combinada (`mockOpenDialog()`), anota o que iria para o navegador ou o Explorador (`app.opened()`), muda o tamanho da janela e retém imagens até o teste liberar. **Os testes nunca usam a internet, chaves de verdade nem os dados do computador.** **Nunca abrir um emulador de verdade nos testes:** o Jogar recebe um `Starter` falso nos testes do Rust, os testes do app usam executáveis vazios, e o teste de maximizar usa uma janela de teste invisível no lugar do emulador. Cada funcionalidade nova ganha testes, e o `npm test` tem que passar antes de juntar uma branch na `desenvolvimento` e antes de lançar versão. **Os testes rodam nos dois lugares:** localmente, com as janelas da versão DEV, e no robô do GitHub.
- **Testes no GitHub (Actions):** `.github/workflows/tests.yml` é o "robô dos testes": a cada envio para a `main` ou a `desenvolvimento` e a cada Pull Request, o GitHub liga um Windows limpo, faz `npm ci`, prepara o Rust (com o que já foi compilado nas rodadas anteriores, pelo `rust-cache`) e roda o `npm test`; o resultado vira o selo ✓ ou ✗ do commit e o selo "Tests" dos READMEs. Se falhar, os resultados do Playwright ficam na rodada (`test-results`). Ver: `gh run list`, `gh run view <id> --log-failed`. **A máquina do robô é diferente de um computador de desenvolvimento:** a tela tem 1024×768 (a janela não chega a 1280×800) e a máquina e o disco são lentos, então lá os testes esperam mais (Vitest: até 30 s por teste; Playwright: 15 s por conferência; o `CI=true` do GitHub liga isso), e a primeira rodada compila o Rust do zero. Alinhar a `desenvolvimento` com a `main` roda o robô de novo no mesmo commit, e o selo do commit só fica ✓ se todas as rodadas dele passarem: se uma falhar por lentidão, `gh run rerun <id> --failed`. É também o primeiro passo para a assinatura grátis da SignPath, que exige o build feito por um robô desses.
- **Perguntar antes:** quando um pedido tiver mais de um jeito de ser feito (interface, filtros, regras), perguntar ao usuário antes de implementar, com opções e uma recomendada. Decisões técnicas internas continuam sendo do agente.
- **Ícones:** lucide-react 1.x. Alguns nomes antigos sumiram (ex.: `Filter` agora é `Funnel`); conferir o nome antes de usar.
- **Smart App Control:** o Windows com o Smart App Control ligado pode bloquear um build script do Rust compilado no release sem as informações de depuração; por isso o `[profile.release.build-override]` do `Cargo.toml` deixa os build scripts com elas. Se outro programa da compilação for bloqueado ("Uma política de Controle de Aplicativo bloqueou este arquivo"), o registro `Microsoft-Windows-CodeIntegrity/Operational` do Windows diz qual foi.
- **Compilação de release:** `src-tauri/build.rs` observa o `package.json` para regenerar os recursos de versão do Windows quando a versão muda. O `npm run dist` usa `scripts/release-build-env.mjs` somente no ambiente do build do Tauri: preserva as flags de ambiente na prioridade `CARGO_ENCODED_RUSTFLAGS` → `RUSTFLAGS` → `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS` → `CARGO_BUILD_RUSTFLAGS` (as duas primeiras prevalecem mesmo vazias; target vazio volta ao build), remapeia o perfil para `/build/user` e o repositório para `/build/app`, nas duas formas de barra, e aplica `/PDBALTPATH:%_PDB%` para guardar só o nome do PDB. As flags são codificadas com o separador do Cargo para preservar argumentos com espaços, sem mudar o ambiente de quem chamou o script. O override de release substitui as `rustflags` dos arquivos de configuração do Cargo; para mantê-las, forneça-as explicitamente por `RUSTFLAGS` ou `CARGO_ENCODED_RUSTFLAGS`. Antes de publicar, conferir a versão nas propriedades do executável e a ausência de caminhos pessoais nos binários e pacotes.

## Privacidade: o que não vai para o GitHub

**Nada do computador de quem desenvolve e nada de uma biblioteca de verdade entra no repositório** — nem em código, nem em teste, nem em captura de tela, nem na documentação. O repositório é público: a regra vale para tudo o que entra nele, inclusive mensagens de commit, Pull Requests, Issues respondidas e releases.

Nunca em arquivo versionado (nem em mensagem de commit, Pull Request ou release):

- **Caminhos com o nome de usuário do Windows.** Escrever `%APPDATA%`, `%USERPROFILE%`, `<pasta do usuário>` ou um caminho de exemplo (`D:\Jogos\...`).
- **Uma biblioteca de verdade:** nomes dos jogos e das ROMs de alguém, tempo jogado, status, pastas de ROMs e onde os emuladores estão instalados.
- **O ambiente do mantenedor:** que programas, emuladores, controles e contas ele tem, configurações do computador dele, onde ficam as chaves e o histórico das conversas com os agentes (pedidos, escolhas e datas).
- **Dados pessoais:** e-mail (os commits usam o `noreply` do GitHub), chaves de API e imagens de outras janelas do computador.
- **Notas do mantenedor:** o estado do projeto, o histórico e as decisões pessoais ficam fora do repositório, e nenhum arquivo daqui aponta para elas.

Como fazer, então:

- **Capturas do README:** montar uma **biblioteca de demonstração** num banco temporário — jogos conhecidos (Tekken 5, Crash Bandicoot, Pokemon Emerald...), com capa de verdade do libretro-thumbnails e tempo jogado inventado — e tirar as capturas dela nos dois idiomas (`PLAYTROVE_SYSTEM_LANGUAGE` em `pt-BR` e `en`), com `PLAYTROVE_DATA_DIR`, `PLAYTROVE_SKIP_EMULATOR_DETECTION=1` e `PLAYTROVE_HIDE_DEV_MARK=1` (sem ele, a marca DEV aparece no logo). Nunca usar pastas de ROMs de verdade.
- **Testes:** nomes de jogos fictícios ou genéricos, como os 12 jogos de exemplo do app.
- **O contexto do ambiente do mantenedor** (caminhos dos emuladores e das ROMs, jeito de conferir na tela) fica fora do repositório, nas notas dele e na memória de cada agente; o Codex não herda a memória do Claude. Pedir esse contexto apenas quando uma tarefa concreta precisar dele, sem importar credenciais, caminhos pessoais ou a biblioteca para arquivos versionados.
- **Antes de cada commit:** conferir o que vai entrar (`git diff --cached`) procurando esses dados; nos commits que mexem em documentação ou capturas, olhar também as imagens.
- **Trava de dados pessoais:** o `.githooks/pre-commit` bloqueia o commit quando uma linha adicionada ou o nome de um arquivo do que vai entrar contém um dos padrões de `$(git rev-parse --git-common-dir)/private-patterns.txt`: um padrão por linha, sem diferenciar maiúsculas de minúsculas, com `#` para comentários. O arquivo fica na pasta `.git` principal, então nunca vai para o GitHub e vale para todas as worktrees do checkout; cada pessoa monta o seu (nome de usuário do Windows, e-mail pessoal, nomes de pastas privadas) e nunca o copia para o repositório. Sem o arquivo, o hook só avisa. Se o bloqueio acusar um dado pessoal, tirar o dado do commit; se for um falso positivo, ajustar o padrão. Nunca contornar com `--no-verify`.

## Git e GitHub

Fluxo do projeto, com o versionamento inspirado no do Electron (https://www.electronjs.org/docs/latest/tutorial/electron-versioning). Vale como autorização permanente do mantenedor para os commits, pushes, branches e Pull Requests descritos abaixo, sem pedir a cada vez. **O mantenedor não precisa lembrar deste fluxo: quem segue é o agente.** O GitHub deve parecer o de um projeto de verdade (referências: Playnite e PCSX2). **Nunca usar a palavra "backup"** em commits, branches, releases ou no README.

### As branches

| Branch | O que é | Como muda |
|---|---|---|
| `main` | Versão estável: sempre igual à última release. É o que o GitHub mostra | Só por Pull Request: numa versão com novidades (com o OK do mantenedor), numa versão de correção (automática, ver abaixo) ou numa correção só de texto (com o OK do mantenedor) |
| `desenvolvimento` | Trabalho do dia a dia; é a branch do checkout principal e do `npm run dev` | Commit a cada tarefa concluída |
| `<nome-da-mudanca>` | Mudança grande ou arriscada | Sai da `desenvolvimento` e volta para ela por Pull Request |

- **Começo de cada sessão:** conferir com `git status -sb`. Se estiver na `main`, trocar com `git switch desenvolvimento`.
- **Travas:** `.githooks/pre-commit` e `.githooks/pre-push` bloqueiam commit e push direto na `main`, e o `pre-commit` também bloqueia dados pessoais (ver "Privacidade"). Elas são ligadas pelo `core.hooksPath` (o script `prepare` faz isso a cada `npm install`). Nunca contornar com `--no-verify`.
- Trocar de branch muda os arquivos da pasta: um `npm run dev` aberto passa a rodar o código da branch atual.

### No dia a dia

- No fim de **cada tarefa que funcionou**, com o `npm run build` passando: commit na `desenvolvimento` e `git push`.
- Mensagens no padrão Conventional Commits (o mesmo do Electron), com o tipo em inglês e o texto em português, no imperativo: `feat: adiciona o modo Detalhes`, `fix: corrige o ícone de restaurar`, `docs: atualiza o README`, `refactor: ...`, `chore: ...`. Primeira linha curta (até ~72 caracteres); corpo com tópicos, se ajudar.
- Nunca fazer commit de código quebrado.
- **Mudanças grandes ou arriscadas:** banco de dados (tabelas e migrações), integrações (Steam, GOG, emuladores, pastas), mudanças em muitos arquivos ou experimentos que o mantenedor pode querer descartar (na dúvida, usar branch).
  1. `git switch -c <nome>` a partir da `desenvolvimento` (nome curto, em português, em kebab-case: `banco-de-dados`, `importar-steam`). No Codex, usar o prefixo `codex/` nas branches novas (ex.: `codex/importar-steam`), mantendo o mesmo fluxo e as mesmas branches de destino. Nas sessões em worktree do Claude Code (as sessões paralelas do app, em `.claude/worktrees/`), a branch começa com `claude/` (ex.: `claude/importar-steam`), pela configuração "Branch prefix" do app, com o mesmo fluxo e as mesmas branches de destino.
  2. Commits na branch e push (`git push -u origin <nome>`), para ela ficar salva no GitHub.
  3. Pronta e testada (`npm test` passando e app conferido): Pull Request para a `desenvolvimento` com um resumo (`gh pr create --base desenvolvimento`), esperar o ✓ do robô dos testes (`gh pr checks <número> --watch`), merge com merge commit apagando a branch (`gh pr merge --merge --delete-branch`), depois `git switch desenvolvimento` e `git pull`.
  4. Se não der certo e o mantenedor concordar: apagar a branch (local e no GitHub). Nada muda na `desenvolvimento`.

### Números de versão

**Só números, no formato `MAIOR.MENOR.CORREÇÃO`** (Versionamento Semântico, o mesmo do Electron). **Sem sufixos** como `-dev`, `-alpha` ou `-beta`.

- **CORREÇÃO** (último número): versão que só corrige erros. Ex.: 0.2.0 → 0.2.1.
- **MENOR** (número do meio): versão com coisas novas; a CORREÇÃO volta a 0. Ex.: 0.2.1 → 0.3.0.
- **MAIOR** (primeiro número): enquanto for 0, o app está em construção. A 1.0.0 fica para quando ele estiver completo para uso.
- O número do `package.json` **só muda no lançamento de uma versão**. Enquanto o trabalho acontece na `desenvolvimento`, ele continua igual ao da última versão lançada.
- Para mudar: `npm version <X.Y.Z> --no-git-tag-version` (atualiza o `package.json` e o `package-lock.json`).
- **Quem decide o número é o `npm run versao`** (`scripts/next-version.mjs`): algum `feat:` desde a última versão → sobe a MENOR; só `fix:` → sobe a CORREÇÃO; só `docs:`/`chore:`/`refactor:` → não precisa de versão. Por isso o tipo do commit tem que estar certo: `feat:` só para o que o app passa a fazer de novo, `fix:` para consertos.
- O mantenedor pode pedir explicitamente um número diferente do sugerido (ex.: publicar como correção ajustes que entraram como `refactor`, como na 0.7.1, ou subir o número do meio numa troca grande que entrou como `refactor`, como a do Electron pelo Tauri na 0.8.0). Nesse caso, não inventar um commit `fix` nem reescrever commits anteriores, e não mudar o cálculo do `npm run versao`.

### Lançar uma versão com novidades: só com o OK do mantenedor

1. Na `desenvolvimento`: conferir o número com `npm run versao` e subir (ex.: 0.1.0 → 0.2.0); atualizar o selo de versão no topo dos dois READMEs (`version-0.2.0` no `README.md` e `vers%C3%A3o-0.2.0` no `README.pt-BR.md`), os "Recursos"/"Roadmap" e, se a interface mudou, as capturas dos dois idiomas em `docs/screenshots/`.
2. `npm test`, commit `chore: prepara a versão 0.2.0` e push. Depois, `npm run dist`, que gera o instalador (assinado com a chave do projeto), a portátil, o `latest.json` e o `latest.yml`, já com o número novo.
3. Pull Request da `desenvolvimento` para a `main` (`gh pr create --base main --head desenvolvimento --title "v0.2.0"`) com o changelog, o ✓ do robô dos testes (`gh pr checks <número> --watch`) e merge com merge commit **sem apagar a branch** (`gh pr merge <número> --merge`).
4. Release: `gh release create v0.2.0 --target main --title "v0.2.0" --notes-file <arquivo> dist/Playtrove-Setup-0.2.0.exe dist/latest.json dist/latest.yml dist/Playtrove-0.2.0-portable.zip`, com notas de changelog para quem visita o projeto ("Novidades", "Mudanças", "Correções" e, se preciso, "Observações"). **Os quatro arquivos vão sempre:** o `latest.json` é o que a atualização do app lê (com a assinatura do instalador), e o `latest.yml` é o que o app em Electron (até a 0.7.x) lê para passar para a versão nova, e a release não pode ser rascunho nem pré-lançamento (o app só enxerga a última release publicada). Depois, `git fetch --tags`.
5. Atualizar a `main` local sem trocar de branch (`git fetch origin main:main`) e alinhar a `desenvolvimento` com ela (`git merge --ff-only main` e `git push`).
6. Conferir se a release é a `Latest` e se o https://github.com/LamarcKz/Playtrove/releases/latest/download/latest.json (e o `latest.yml`, ao lado) mostra a versão nova: é ele que a atualização automática lê.
7. Conferir a execução de `website.yml` e o `Publish site` no `Playtrove-site`: as notas publicadas são a fonte do post, e o rótulo dos guias identifica o snapshot revisado compatível. Atualizar os guias exige revisar os dois idiomas. Edições, remoções, despublicações e conversões de uma estável em pré-lançamento também pedem reconstrução, para o site selecionar novamente as releases publicadas e estáveis. O listener precisa existir no commit da tag; tags antigas não recebem o arquivo retroativamente. Para importar ou corrigir essas releases, executar manualmente o `deploy.yml` do site na `main`. Se uma release passar a ser criada por `GITHUB_TOKEN` dentro do Actions, o workflow que a publica também deve pedir esse dispatch, sem depender de outro evento automático.

### Versão de correção: automática

Quando, desde a última versão, só entraram correções (o `npm run versao` diz "Só correções"), o agente lança a versão de correção **sozinho**, logo depois de corrigir e testar, e avisa o mantenedor com o que foi corrigido. Versões com novidades (número do meio) e a 1.0.0 continuam só com o OK dele.

- Antes de lançar: `npm test` e testar no app a correção e o que ela pode afetar.
- Se a `desenvolvimento` só tem essas correções desde a última versão: os mesmos passos de "Lançar uma versão com novidades".
- Se a `desenvolvimento` já tem novidades ainda não lançadas: fazer a correção numa branch a partir da `main` (`git switch -c corrige-<assunto> main`), com a versão `0.2.1`, Pull Request para a `main` e release `v0.2.1`. Depois, levar a correção para a `desenvolvimento` com `git switch desenvolvimento` e `git merge main`. Assim as novidades não saem junto.

### Correção só de texto na `main`

Serve para consertar um texto da página do projeto (ex.: o `README.md`) sem esperar a próxima versão. Só com o OK do mantenedor. O número não muda e não há release.

- Se, desde a última versão, a `desenvolvimento` só teve mudanças de texto: Pull Request dela para a `main`, merge com merge commit sem apagar a branch e, depois, o passo 5 de "Lançar uma versão com novidades".
- Se ela já tem código novo: fazer como na versão de correção (branch a partir da `main`, Pull Request para a `main` e `git merge main` na `desenvolvimento`), mas sem mudar o número e sem release.

### Desfazer

- Mudanças ainda sem commit: guardar com `git stash push -u -m "<motivo>"` (dá para recuperar) em vez de apagar com `git restore`/`git clean`.
- Commit já feito: `git revert <commit>` (para desfazer o merge de uma branch: `git revert -m 1 <merge>`). Nunca `reset --hard` + `push --force` na `main` ou na `desenvolvimento`.
- Para só olhar como estava: `git switch --detach <commit>` e depois `git switch desenvolvimento`.
- Para voltar a uma versão: baixar o "Source code (zip)" da release ou usar `git switch -c <nome-da-branch> vX.Y.Z`.
